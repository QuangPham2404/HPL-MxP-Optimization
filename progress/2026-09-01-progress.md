## Baseline parameters chosen (per user)

  `nprow × npcol = ranks` (square-ish, `npcol >= nprow`). 8 ranks => 2x4 exactly.

## What works

- Launch: 2x2 job allocated 2 distinct nodes (hpc-gaas-g08, g09), spawned 4 ranks,
  correct per-rank GPU visibility, grid 2x2. Same mechanism as the validated probe.
- IB is fully visible inside the container on compute nodes (UCX: rc/ud/dc_mlx5,
  `mlx5_bond_0` + individual devices, PORT_ACTIVE).

## What fails (blocker)

- Cross-node `MPI_Init` hangs: the HPL run (and a minimal 2-node `MPI_Allreduce`
  test) never prints "after MPI_Init"; jobs hit walltime. Single-node HPL works.
- Not an env-pollution issue: dropping `-x LD_LIBRARY_PATH` did not fix it, and
  ldd confirms the app correctly links the container's own `libmpi.so.40` via RPATH.

## Root cause (hypothesis, needs user decision)

Host `mpirun` (host HPC-X) drives a container MPI app (container HPC-X at
`/opt/hpcx`). The container ranks' `libopen-rte/libopen-pal` cannot complete the
cross-node ORTE/PMIx session with the host `mpirun`, so `MPI_Init` blocks. This is
a launcher-strategy gap: the documented GAAS bridge validates rank *spawn* only,
not MPI *communication*.
